<Breakpoint id="context">

DomoNow es la plataforma SaaS de Ofima para administrar conjuntos residenciales: accesos con QR, reservas de zonas comunes, asambleas con votación en tiempo real, cartera, alertas de pánico y más. Son microservicios .NET y micro-frontends Angular repartidos en **34 repositorios**, con un equipo de unas 20 personas.

Además de desarrollar módulos completos, soy responsable de la infraestructura Azure, de los releases, de revisar e integrar pull requests y de capacitar al equipo. Este caso cuenta cómo llevamos la IA al proceso de desarrollo de todo el equipo.

</Breakpoint>

<Breakpoint id="problem">

El equipo ya usaba asistentes de IA, pero cada agente trabajaba a ciegas: no conocía las convenciones de arquitectura, duplicaba lógica entre microservicios y no sabía qué repositorio tocar cuando un cambio cruzaba backend y frontend. Más IA sin reglas solo producía más código que revisar.

</Breakpoint>

<Breakpoint id="architecture">

Junto con otro desarrollador montamos un **Store central de specs** con OpenSpec que gobierna los 34 repositorios. Yo escribí las skills, la mayoría de los cambios y las reglas técnicas, y lo probé con el módulo piloto de Parqueaderos antes de extenderlo.

</Breakpoint>

<Breakpoint id="decisions">

### Reglas antes que prompts

Escribí cerca de 200 reglas técnicas con identificador, enunciado normativo y ejemplo (estructura de proyecto, CQRS, repositorios, componentes, design system, rutas). Las siguen tanto las personas como los agentes, y una skill específica detecta duplicados y contradicciones antes de añadir una nueva.

### Skills que hacen el trabajo repetitivo

Creé 8 skills propias de Claude Code: conectar un módulo al Store, reconstruir historias de usuario y reglas de negocio leyendo el código con dos agentes en paralelo, auditar una API .NET contra la arquitectura de referencia y versionar micro-frontends.

### Límites claros para la IA

El agente nunca ejecuta git ni SQL; los pasos que debe hacer una persona se marcan como tareas `[DEV]`, y el modelo se elige por fase: uno más capaz para explorar y proponer, otro más rápido para aplicar.

### Automatizar el release

Promover a producción era un proceso manual, repositorio por repositorio, sobre unos 30 repositorios. Lo especifiqué con el mismo flujo y lo automaticé con la API REST de Azure DevOps: detecta qué cambió, respeta el orden de las librerías compartidas, crea las ramas y abre los PR, con modo simulación por defecto.

</Breakpoint>

<Breakpoint id="code">

Cada skill declara qué modelo usa y que solo se invoca a mano, para que ningún agente la dispare por su cuenta:

</Breakpoint>

<Breakpoint id="results">

El Store acumula más de 1.100 tareas completadas, y yo redacté 50 de sus 52 cambios. La guía de adopción que escribí (17 secciones) es el material con el que capacitamos al equipo. Con el script de promoción, un release deja de ser una tarea manual por repositorio y pasa a ser una ejecución revisable.

</Breakpoint>

<Breakpoint id="learnings">

- La IA amplifica lo que ya hay: sin reglas amplifica el desorden; con reglas, el estándar.
- Las specs son el contrato entre personas y agentes, y también entre repositorios.
- Los límites (sin git, sin SQL, tareas `[DEV]`) son lo que permite confiar en el agente.
- Un piloto pequeño (Parqueaderos) convence más al equipo que cualquier presentación.

</Breakpoint>
